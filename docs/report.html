Technical report

Building a kernel-bypass VPC overlay, one byte at a time

Light-Andromeda is a from-scratch miniature of the software layer cloud providers run under every VM — the thing that gives a tenant a private network that isn't real. It parses packets by hand, wraps them in a custom overlay, forwards them by a centrally-programmed map, and moves them in user space past the kernel's network stack with AF_XDP. A real ping travels through it.

01The problem

Tenant A's VM at 10.0.0.10 wants to reach its other VM at 10.0.0.20. They sit on different physical hosts, on a fabric that knows nothing about 10.0.0.0/24 — and that is carrying other tenants who also use 10.0.0.0/24. Host software has to intercept the raw frame, decide which physical machine hosts the destination right now, wrap the frame so the fabric can carry it without understanding tenant addresses (and without collisions), unwrap it on the far side, and do it fast enough to never be the bottleneck.

That is network virtualization. Getting the last two — correct isolation and speed — is the whole game, and it's what this project is about.

02How it's built

A Rust workspace with a clean split between the data plane (fast, per-packet) and the control plane (slow, "where does 10.0.0.20 live?") — the same separation a real SDN uses.

03The overlay on the wire

An inner tenant frame is wrapped as L2-over-UDP — the same shape as VXLAN/GENEVE — with a custom 8-byte header carrying the tenant id and a flow hash:

Outer IPv420 B

inner tenant framethe VM's packet
  • VNI (24-bit) — the tenant id, so overlapping 10.0.0.0/24 spaces stay isolated.
  • Flow hash (16-bit) — a hash of the inner 5-tuple, also written into the outer UDP source port so the underlay's ECMP spreads flows without opening the tunnel.
  • Hop limit — an overlay TTL against encapsulation loops.

Dissect it live: the browser playground and andromeda inspect build byte-identical packets — verified two ways.

04Making it fast

single core · AMD Ryzen 5 5600 · release build · microbenchmark of the forwarding logic · mean of 7 trials (1 warm-up discarded) · 60-byte inner frame, east-west encap

The first working version did 19 Mpps. Six changes — each standard dataplane practice, none of them gaming the benchmark — took the encapsulation core to ~90 Mpps:

Reading the chart: the big jumps are removing work, not clever tricks. Stop copying the frame twice. Stop scanning the payload for an outer UDP checksum the spec lets you omit (RFC 6935, exactly what VXLAN does). Replace a per-packet hash built to resist collisions (SipHash) with one built to be fast. Precompute the constant outer header once. And finally, when the frame is already in the AF_XDP buffer, stamp the header into its headroom and never copy the payload at all.

Compute- or memory-bound? A controlled experiment

Batching frames didn't beat a single hot frame — which looked like a memory bound. That reasoning is too crude: one reused frame is L1-resident and flatters the result. The honest test sweeps the working-set size (4 KB → 64 MB) under two access orders — sequential (as packed, prefetcher-friendly) and shuffled (random frame order, defeating the prefetcher, closer to how a NIC hands back recycled buffers):

The experiment refutes the guess — and says something sharper. Sequential access is flat at ~80 Mpps across five orders of magnitude of working set: the hardware prefetcher hides all latency, so the code is compute-bound. Random access tracks the cache hierarchy exactly — level inside L2, a knee at the 512 KB L2 boundary, and a collapse to ~9 Mpps (9× slower) once the set exceeds the 32 MB L3 and every packet pays a DRAM miss: memory-latency-bound. The regime depends on locality, not the code — and reporting only the cache-hot number would overstate real-world throughput by up to 9×. That's also why there's no fake "100 Mpps" from a single-flow cache here: it would "win" only on this single-flow benchmark.

The switch pulled and encapsulated 100% of the offered load with zero receive drops; the bottleneck was the veth's copy-mode TX path and the generator, never the dataplane. On a real NIC with native, zero-copy XDP that gap closes — showing it is future work, not a WSL2 experiment.

06Honest limitations

  • The headline numbers are an in-cache single-core microbenchmark of the logic — clearly labelled, not a line-rate claim.
  • WSL2 + veth + generic XDP is well below a real NIC in native/zero-copy mode; the live numbers reflect that environment, not the design's ceiling.
  • Scope is deliberately narrow: single VPC, IPv4, provisioned endpoint table (no MAC learning), no fragmentation or encryption. Depth on the core mechanism over breadth.

It's a portfolio project — a deliberately small, complete, and honest implementation of a large idea.
